# project-builder — Product Spec ที่แยกขอบเขตแล้ว

วันที่: 7 พฤศจิกายน 2026 (Asia/Bangkok)
สถานะ: จัดขอบเขตใหม่ตามคำแก้ไขของเจ้าของ; ข้อกำหนดจากเจ้าของแยกจากข้อเสนอ implementation
เอกสารนี้อธิบาย **ตัวปลั๊กอินและงานที่มันทำให้โปรเจ็กต์ที่รับผิดชอบ** แผนสร้างตัวปลั๊กอินอยู่ [อีกเอกสารหนึ่ง](../development/plugin-build-plan.md)

## 1. นิยามที่ใช้ตรงกัน

- **ตัวปลั๊กอิน**: project-builder ที่กำลังสร้าง เพื่อให้เจ้าของและเพื่อนนำไปใช้กับ AI agent
- **โปรเจ็กต์ที่รับทำ**: งานที่ผู้ใช้เรียก project-builder ไปช่วย เช่น ระบบของลูกค้า มินิโปรเจ็กต์มหาวิทยาลัย หรือฟีเจอร์เวอร์ชันใหม่
- **Stage**: PoC, MVP, Beta, Final ของโปรเจ็กต์/ฟีเจอร์ที่ปลั๊กอินรับทำ ไม่ใช่ระดับความคืบหน้าของการสร้างปลั๊กอินในแชตนี้
- **งานสร้างปลั๊กอิน**: ออกแบบ เขียนโค้ด ทดสอบ แพ็ก และเขียนคู่มือให้ project-builder ใช้งานได้ ใช้ Native ได้ ไม่มีข้อบังคับให้จำลององค์กรหรือเดินทุก Stage
- **QA matrix ของโปรเจ็กต์ที่รับทำ** กับ **ชุดทดสอบโค้ดปลั๊กอิน** เป็นคนละชุด ชุดหลังต้องพิสูจน์ว่าปลั๊กอินใช้กฎชุดแรกถูกต้อง

## 2. ข้อกำหนดพื้นฐานของตัวปลั๊กอิน

ชื่อ project-builder สำหรับเจ้าของและเพื่อน รองรับ Codex, Claude Code, Devin เฉพาะ CLI/Desktop บน Windows และ macOS ใช้แกนกลางเดียวและ adapters แต่ละ host

CLI/Desktop ในที่นี้คือช่องทางของ AI agent ที่โหลดปลั๊กอิน ไม่ใช่ข้อกำหนดให้สร้าง CLI agent หรือ Desktop application ใหม่อีกชุด ส่วนคำสั่ง CLI/helper ภายในเพิ่มได้เมื่อจำเป็นต่อการทำงาน

การรองรับ OS/host เป็นเป้าหมาย compatibility ของตัวปลั๊กอิน ไม่ใช่ข้อบังคับว่าทุกโปรเจ็กต์ที่รับทำต้องรองรับทั้งสอง OS หรือใช้ agent ทั้งสามตัวพร้อมกัน ผลทดสอบ compatibility ต้องระบุสิ่งที่รันจริงและสิ่งที่ยังไม่ได้รัน

แกนกลางเดียวไม่ได้แปลว่าต้องสร้าง server, daemon, database หรือ framework ทุกอย่างก่อนเสมอ รูปแบบ instructions, state, scripts และ deterministic guards เป็นการตัดสินใจทางวิศวกรรมที่ต้องอธิบายว่าจำเป็นต่อพฤติกรรมใด ไม่ใช่คำสั่งให้ทุกโปรเจ็กต์ลูกค้าใช้ tech stack เดียวกัน

## 3. งานที่ปลั๊กอินต้องรับได้

1. เริ่มโปรเจ็กต์จากศูนย์
2. รับงานที่ทำไม่เสร็จ แล้วพาต่อจนส่งมอบตาม scope
3. รับระบบเดิมเพื่อพัฒนาเวอร์ชัน/ฟีเจอร์ใหม่

เมื่อรับงานเดิม ต้องสำรวจ code, requirements, runtime/dependencies, สถานะ Git, ฟีเจอร์ที่ใช้งานได้ ปัญหา และข้อจำกัดก่อนสรุปแผน ห้ามเดาว่างานที่มี code อยู่เท่ากับใช้งานได้แล้ว

ก่อนรันระบบเดิมเพื่อเก็บ baseline ให้ตกลงสิทธิ์ setup/access และข้อมูลทดลองในขอบเขต discovery ก่อน โดยไม่ต้องแสร้งว่าสรุป requirement สมบูรณ์แล้ว

กรณีรับงานต่อ ต้องมี baseline trial จากผู้ใช้จริงตามข้อ 9 เพื่อให้ปัญหา UX/UI เป็นข้อมูลตั้งต้นของ requirement ไม่ใช่รอจนพัฒนาเสร็จค่อยเห็นปัญหาเดิม

## 4. Requirement discovery และ kickoff

ปลั๊กอินต้องถามให้ได้คำตอบที่ชัดจาก business level ถึง technical level ได้แก่ ปัญหา/คุณค่าธุรกิจ ผู้ใช้ เป้าหมาย scope ฟีเจอร์ acceptance constraints UX/UI data/integrations architecture environment คุณภาพ ทรัพยากร สิทธิ์ และสิ่งที่จะส่งมอบ

ใช้ข้อมูล repo และคำตอบเดิมก่อนถามซ้ำ แยกข้อเท็จจริง คำยืนยัน สมมติฐาน และสิ่งที่ยังไม่ทราบ คำถามที่เปลี่ยน scope/acceptance/authority ต้องไม่ถูกตอบแทนผู้ใช้ด้วยการเดา

ก่อนเริ่มรอบทำงาน ให้ผู้ใช้รีวิวสิ่งที่จะทำ ขอบเขตที่ไม่รวม แผนตรวจรับ ทีมที่จำเป็น งบทรัพยากร อำนาจ และวิธีรัน local ให้พอทำงานต่อเนื่องจนได้ชิ้นงานตามที่ตกลง การหยุดถามยังจำเป็นเมื่อเจอ blocker ที่ตัดสินใจแทนไม่ได้หรือคำสั่งที่ต้องหยุดทันที

## 5. Stage และ Agile/Scrum ภายในปลั๊กอิน

- ประเมิน PoC/MVP/Beta/Final ทุกครั้งในระดับโปรเจ็กต์หรือฟีเจอร์
- ใช้ Stage ให้น้อยที่สุดตามฟีเจอร์ที่ใช้งานได้จริงเทียบ requirement และความเสี่ยงที่ยังต้องพิสูจน์ ตามแนวคิด min of max ของเจ้าของ
- ไม่บังคับผ่าน PoC → MVP → Beta → Final ครบทุกชื่อ และไม่สร้าง Beta เพียงเพื่อให้ครบลำดับ
- ใช้ Agile/Scrum เพื่อบริหาร backlog, work items, dependencies และรอบพัฒนาให้เหมาะกับ scope; sprint หรือ task ไม่ใช่ maturity Stage เพิ่ม
- ทุก Stage ที่เลือกทำจริงต้องมีขอบเขต เกณฑ์ตรวจรับ และ local user guide
- แยกจบรอบพัฒนาออกจากปิด Stage หลัง feedback/การตรวจรับ เพื่อไม่อ้างว่าจบก่อนเห็นผลที่จำเป็น

ข้อกำหนดนี้คือความสามารถของ Stage selector/workflow ในปลั๊กอิน **ไม่มีคำสั่งให้นำมาจัด Stage ของการสร้างตัวปลั๊กอินเอง**

## 6. ทีมและการบริหารทรัพยากร

บทบาทที่ต้องรู้จัก: BA, PM, SA, Development Lead, BE, FE, Data Engineer, AI Engineer, QA (SIT/UAT), UX/UI Designer และ DevSecOps

เลือกใช้เฉพาะบทบาทและการแยก agent ที่จำเป็นต่อขนาด/ความเสี่ยงของงาน บางบทบาทรวมความรับผิดชอบได้ ไม่เปิด agent ครบรายชื่อเพียงเพราะมี role catalog และไม่ใช้กระบวนการหนักเกินมินิโปรเจ็กต์

ปลั๊กอินต้องรู้ว่างาน/โปรเซส/browser/container/ไฟล์ใดเป็นของ run ใด มีงบและ lifecycle ที่ชัด หยุดและเก็บกวาดของชั่วคราวเมื่อจบ ล้มเหลว ยกเลิก หรือกู้คืนจาก crash รักษาของผู้ใช้และทรัพยากรที่ใช้ร่วมกัน ไม่รับประกันความสามารถของ OS เกินที่ตรวจได้จริง

ความระมัดระวังด้านทรัพยากรยังเป็นหน้าที่ปกติของผู้สร้างปลั๊กอินด้วย แต่ไม่ได้ทำให้ผู้สร้างต้องจำลองทีมภายในปลั๊กอินระหว่างเขียนมัน

## 7. Git workflow ที่ปลั๊กอินต้องจัดการให้โปรเจ็กต์ที่รับทำ

ก่อนงานพัฒนา ตรวจ/สร้าง main, staging, develop เฉพาะที่ขาด โดยไม่เขียนทับ refs เดิมและใช้ baseline ที่ตกลง

เส้นทางทำงาน: develop → Stage branch → feature branch
เส้นทางรวมงาน: feature → Stage → develop

เก็บ Stage branch; feature branch เลิกเก็บได้เมื่อยืนยันว่ารวมงานครบและไม่มีงานใหม่ค้าง ชื่อเช่น stage/<scope>/mvp เป็นตัวอย่าง implementation ไม่ใช่ชื่อบังคับที่เจ้าของระบุ

อำนาจตกลงเป็นรายงาน แต่เพดานของ **ตัวปลั๊กอิน** สูงสุดคือเปิด PR เข้า staging ห้ามเพิ่มเพดานด้วย user prompt, role, add-on หรือคำสั่งอ้อม ห้าม merge/auto-merge/enqueue เข้า staging, เขียน main หรือไป prod แทนผู้ใช้

กฎ Git นี้เป็นสิ่งที่ต้อง implement/test ในปลั๊กอิน ไม่ใช่คำสั่งให้ผู้สร้างใช้ Stage branches แบบเดียวกันกับ repo ของปลั๊กอิน การทำ Git จริงในงานสร้างใช้ขอบเขตที่เจ้าของมอบหมายตามปกติ

## 8. QA, test matrix และเครื่องมือ

ข้อกำหนดคุณภาพจากเจ้าของ: ผลผ่านต้อง **มากกว่า 95%** ของ applicable test cases ตาม matrix และไม่มีปัญหา **High ขึ้นไป** ค้าง จึงต้องทดสอบกรณี 95% ไม่ผ่าน, มากกว่า 95% ผ่านในเชิงอัตรา และ High บล็อกแม้อัตราสูง

Matrix ต้องเชื่อม requirement/acceptance/test/result/defect และเลือกประเภทที่จำเป็นต่อ scope เช่น functional, regression, integration/SIT, UAT, E2E, UX/UI, accessibility, performance/load, security และ data/AI เมื่อเกี่ยวข้อง ไม่บังคับทุกหมวดกับทุกมินิโปรเจ็กต์ และไม่ตัดเคสเพื่อปั่นคะแนน

ปลั๊กอินต้องรู้วิธีใช้ Playwright และเลือก add-ons ที่จำเป็น ไม่ติดตั้ง browser/tools ทุกชุดให้ทุกโปรเจ็กต์ การทดสอบอัตโนมัติไม่แทน usability feedback ของคนจริง

**ประเด็นที่เอกสารเดิมตีความเพิ่ม:** การเขียนว่าเกณฑ์ >95%/High+ ใช้เฉพาะ Final เป็นรายละเอียดที่ผู้ออกแบบใส่เพิ่ม คำของเจ้าของไม่ได้จำกัดไว้เฉพาะ Final โดยตรง ต้องกำหนดการใช้ gate ต่อ Stage ให้ชัดใน product contract; อย่าอ้างว่าจังหวะนั้นเป็นคำยืนยันจากเจ้าของ และอย่านำเกณฑ์นี้ไปตั้งเป็น maturity gate ของงานสร้างปลั๊กอินเอง

## 9. ผู้ทดลองจริงและ EGM

สำหรับโปรเจ็กต์ที่ปลั๊กอินรับทำ ต้องมีผู้ใช้จริง 2–3 คนที่ไม่มีบริบทภายในและไม่รู้จักกัน ให้ feedback อย่างอิสระ:
- ครั้งแรกที่รับโปรเจ็กต์เดิมมาทำต่อ เพื่อช่วยสร้าง requirement
- หลังจบรอบพัฒนาของแต่ละ Stage ที่เลือกทำจริง

ปลั๊กอินต้องช่วยเตรียม task pack/แบบเก็บผล รับ feedback แยกคน เชื่อมปัญหากับ requirement/defect/backlog และรายงานสิ่งที่ยังรอ ห้ามสร้างผู้ทดลอง/ผลแทนคนจริง ห้ามส่งคำเชิญแทนโดยไม่ได้รับคำสั่ง

Elephant-Goldfish Model เป็นแนวทางสำหรับผู้ประสานงานที่รู้บริบทและผู้ตรวจที่เริ่มบริบทใหม่ ปรับใช้ได้ สิ่งนี้แยกจากผู้ทดลองจริง 2–3 คน

นี่คือ workflow ที่ต้องสร้าง ไม่ใช่การให้เจ้าของจัดหาผู้ทดลองมาทดสอบการเขียนปลั๊กอินทุกช่วง

## 10. Environment และ local guides

รองรับข้อจำกัด runtime/dependency ของโปรเจ็กต์ที่รับช่วง เช่น Python รุ่นเดิม ใช้ interpreter/version manager และ project environment ให้ถูกหน้าที่ ไม่เปลี่ยน Python/PATH/profile/global packages ของเครื่องผู้ใช้เงียบ ๆ

เมื่อ prerequisite ไม่พร้อม ต้องบอกวิธีตั้งค่าทีละขั้น วิธีตรวจผล และสิ่งที่จะเปลี่ยน พร้อมใช้วิธีแยก environment ที่เหมาะกับ Windows/macOS เช่น pyenv/pyenv-win หรือเครื่องมือที่มีอยู่แล้ว

ทุก Stage ของโปรเจ็กต์ที่รับทำต้องมีคู่มือ setup/config/run/stop/cleanup/troubleshooting ที่ตรงกับ build ของ Stage นั้น ส่วนตัวปลั๊กอินต้องมีคู่มือติดตั้งและใช้งานปลั๊กอิน ไม่ต้องสร้างคู่มือ PoC/MVP/Beta/Final ของการเขียนปลั๊กอินเอง

Python/MCP/SQLite/PyInstaller/เลขเวอร์ชันที่เคยเลือกสร้างปลั๊กอินเป็นข้อเสนอ implementation ไม่ใช่ข้อกำหนดว่าระบบลูกค้าต้องใช้สิ่งเหล่านั้น

## 11. คำสั่งและเหตุการณ์ระหว่างงาน

UX กลาง: /project-builder:init, :start, :continue, :status และคำสั่งรองที่ช่วยใช้งาน เช่น help, doctor, guide, change, backlog, feedback, pause/cancel/cleanup โดย adapter ใช้รูปแบบที่ host รองรับจริง

ไอเดีย/requirement ใหม่ที่ไม่เร่งด่วนระหว่าง Stage ของโปรเจ็กต์ที่รับทำ ให้บันทึก backlog ทันที แต่ไม่ขยาย scope รอบนั้น ทำ Stage ที่ตกลงไว้ให้จบก่อนทวนกับผู้ใช้ ไม่ใช่รอแค่จบ task หรือ sprint

คำสั่งหยุด/ยกเลิก และเหตุเร่งด่วนที่ต้องแก้ขอบเขตต้องได้รับการจัดการทันที คำถามสถานะไม่ยกเลิกงานเดิม คำสั่งซ้ำหรือ worker เก่าต้องไม่สร้างงาน/โปรเซส/PR ซ้ำ

กฎ backlog นี้ไม่ได้บังคับให้รอจบ Stage สมมติ เมื่อเจ้าของแก้ความเข้าใจเกี่ยวกับการสร้างตัวปลั๊กอินในแชตนี้

## 12. สิ่งที่ยังเป็นการตัดสินใจของผู้สร้าง

รูปแบบ package/adapters, storage, ภาษา/runtime, ความจำเป็นของ MCP, internal APIs, branch naming, merge strategy, resource thresholds และการบังคับใช้ที่แต่ละ host ทำได้ ต้องมีเหตุผลและหลักฐาน ไม่ถือว่าการตอบ “โอเค” อนุมัติสมมติฐานทุกอย่างโดยปริยาย

ข้อความในเอกสารเก่าที่ขัดกับการแยกขอบเขตฉบับนี้ใช้เป็นบันทึกประวัติเท่านั้น แผนสร้าง 19 งานเดิมที่ติดป้าย Stage ถูกยกเลิกการใช้เป็นแผน execution ปัจจุบัน
