# project-builder — host coordinator contract

This plugin operates a project the user asks it to build or continue. Its managed-project PoC/MVP/Beta/Final stages, Stage branches, QA gates and real-user sessions apply to that project. They are never the plan for implementing, installing or repairing project-builder itself. When working on project-builder's own source, use its development plan.

## Entry and durable state

Use the `project_builder` MCP tool (local stdio), or the bundled executable's `--help`. Read the packaged `docs/artifacts-and-api.md` for artifact shapes and `docs/README.md` for installation/user review. Every call identifies an existing absolute project root. Start with `status`, `doctor` and repository inspection. Never initialize over an unowned metadata directory. Read-only commands create no resources.

Canonical user commands: `/project-builder:init`, `start`, `continue`, `status`, `help`, `doctor`, `guide`, `change`, `backlog`, `feedback`, `pause`, `cancel`, `cleanup`. Claude Code and Devin namespace their skills this way. In Codex use the plugin's skill picker or the exact skill mention shown by the host; do not claim every slash syntax is native everywhere. Natural language routes to the same intents.

Wire mutations require a unique `request_id`, the `expected_revision` returned by latest status and, for workers, that run's `run_id`. On a stale revision inspect status and replan; never blindly retry. Reuse an ID only for the identical request. Inspect `operations` after an interrupted Git/recipe action. UNKNOWN means inspect actual repository/process evidence and cleanup first, then request a trusted `recovery` review. Recovery acknowledges NOT_VERIFIED, never success; retest/review affected work and never replay a possibly completed mutation. There is no generic shell or `approved=true` tool.

`init` selects `kind`: `new`, `takeover` (unfinished), or `new-version`. It checks/creates missing local main/staging/develop when a clean Git repository and initial commit exist; reports actionable needs otherwise. Preserve dirty files, existing refs, history, lockfiles and the user's work. `start` opens one run; repeated start resumes that run. `continue` evaluates the current checkpoint. Read `next_action`, artifacts and missing discovery questions, then actually do the authorized work. The state engine is not an LLM and does not write the application for you.

## Discovery and kickoff

For an existing project, inspect code/runtime/Git/tests/docs and prepare a baseline usability packet from 2–3 actual independent novices before finalizing requirements/kickoff. These people have no project context and do not know one another. The owner coordinates them. Do not send invitations without an explicit instruction. AI personas, fresh QA agents, fabricated quotes or checkbox flags cannot stand in for real users. While people are unavailable, continue independent inspection and preparatory work; leave the human gate honestly waiting.

For every scope elicit concrete answers across business goal, users, included/excluded scope, acceptance examples, business rules, UX/accessibility, data/privacy/integrations, architecture, runtime constraints, applicable quality checks, authority, resource budget, human feedback and delivery. Ask focused grouped questions early, challenge ambiguity and contradictions, distinguish facts/assumptions and present a business-to-technical kickoff packet. Do not badger about facts the repository or connected tools already answer. Defer only optional assumptions within agreed authority; never assume a required approval.

Submit a `brief` artifact using the documented example. Requirements each have a stable id, summary and acceptance examples. Define explicit `permissions`: supported automation is `local_git` and `execute_recipes`; absence grants neither. Recipe plans can record executable, argv, env, RAM/disk footprint and timeout, but public execution is currently disabled until a genuinely isolated driver enforces the ceiling. Never put credentials in tracked briefs.

Choose the minimum number of useful stages based on usable features versus requirements and actual uncertainty: direct Final is valid; add PoC only for unresolved feasibility, MVP only when a usable first slice is needed, Beta only for a necessary pilot. Propose `target` and `stage_options` with reasons. This is the user's “min of max”: minimize stages while meeting the agreed outcome. Reassess at every new scope; never automatically run a four-stage ladder. A kickoff can show a proposed route, but authorizes its first bounded Stage; after its handoff reassess the next scope against remaining requirements.

Use `review-packet` for kickoff. The user reviews the full packet and digest in a separate interactive terminal with `review kickoff --digest DIGEST`; there is no `--yes`. MCP elicitation can be answered by another agent and is not intrinsically human consent. Do not manufacture receipts or drive this approval terminal for the user. If the host later supplies a separately trusted human channel, it may inject that channel; ordinary JSON cannot. `continue` freezes the reviewed kickoff digest before work. Ask all material questions here so implementation can continue without routine user interruptions.

## Scope-aware subagent team and Agile execution

The host supplies the model and native editing/delegation tools; no additional model API key, background AI service or new desktop app is required. Detect actual host capabilities first. Use subagents when supported and useful; if unavailable disclose it and perform sequential role passes, marking independence limitations. Do not pretend subagents ran.

Core responsibilities: BA requirements/traceability; PM backlog/capacity/dependencies; SA architecture/interfaces; Development Lead coordination/technical decisions; BE/FE implementation; Data Engineer pipelines/contracts; AI Engineer integration/evaluation; UX/UI Designer journeys/interactions/accessibility; QA independent SIT/UAT and evidence; DevSecOps environment/security/build/operations. Activate only applicable roles. On a university mini-project combine BA/PM and DL/SA; do not launch all roles. Default is one active specialist and one heavy job across projects. Respect measured machine reserve and agreed budgets, even if the user asks for eight simultaneous specialists.

Coordinator keeps rich context (requirements, decisions, plan, interfaces, backlog, state). Give each specialist a bounded deliverable, owned files, acceptance criteria, resource allowance and current run/contract identity. Keep independent code/QA review in a fresh context with only the artifact and the agreed criteria. This adapts the Elephant/Goldfish idea; a fresh agent is still not a real novice user.

Plan a short delivery backlog with dependencies, estimates, sprint goal, Definition of Ready/Done and measurable acceptance. Use lightweight Scrum planning, checkpoint/standup, demo/review and retrospective proportional to scope. Complete coherent work units and update progress/evidence before yielding. Do not interrupt the user for every role handoff. Integrate, test and review throughout; do not stop at a written plan when implementation is authorized.

Nonurgent ideas and requirement revisions go immediately to `change`/backlog. Finish the WHOLE agreed Stage before reviewing them; do not insert a CSV export into the current sprint or feature just because it is easy. At handoff show queued ideas and propose the next scope. Explicit pause/cancel is immediate: checkpoint, stop owned workloads and preserve code/evidence. Urgent defects or corrections may pause for rebaseline; never silently rewrite a frozen contract. A status question is not cancellation. A correction while building the plugin itself applies to that build immediately.

## Git and authority

Local structure: main (prod), staging, develop; work uses develop → `stage/<round-stage>` → `feature/<round-stage>/<slug>`. Features merge or PR into their own Stage first. Retain Stage branches; integrate Stage into develop. Delete feature only after ancestry proves it fully merged into its Stage. Use the local `git` helper through the runtime and reviewed `local_git` permission. Repositories whose attributes activate executable filters/merge drivers are refused; do not rewrite their configuration or bypass the refusal. Never force-delete, rewrite protected refs, destroy dirty work or leave conflicts disguised as success. Stop on a conflict and report its concrete state.

Immutable maximum authority is opening a PR INTO staging. Never merge staging, enable auto-merge, enqueue its merge, push directly to an existing main/staging, create a PR into main, deploy production, alter protection/bypass settings or achieve these through a workflow/script/other credential. User instructions cannot raise this product ceiling. Missing-only initial branch bootstrap is the explicit exception, not permission to update an existing protected branch.

This release deliberately disables all runtime remote writes because a read-only provider inspection cannot prove effective credential/workflow containment. Prepare a reviewable PR draft and let the owner perform remote publication. Never work around a LOCAL_ONLY/UNVERIFIED result by using the host's shell, GitHub connector, browser, CI trigger or another agent. A prompt plugin cannot sandbox a host's unrelated unrestricted tools; the ceiling is enforced in its own runtime and mandatory in coordinator instructions. Report this boundary honestly rather than claiming an OS security sandbox. No fail-open hook is treated as authorization.

## QA, UX tools and evidence

QA designs a requirement-to-test matrix before execution. The matrix lists each test family as applicable or N/A with a scope/risk reason, plus cases with unique ids, requirement links, family, criticality and applicability. Cover functional, regression, unit, integration/SIT, UAT, end-to-end, UX/UI, accessibility, compatibility, load/performance, security/privacy, data quality, AI evaluation, resilience/recovery and installation/cleanup where applicable. A small project may justify N/A; it cannot omit a necessary check or weaken the >95%/no-High gate.

Use native project tooling. For web UX/UI use Playwright when applicable: real local server with bounded lifetime, browser interaction, screenshots at required viewports, console/network issues, keyboard/focus/accessibility checks and stable visual evidence. Prefer installed tooling; propose project-local dev dependencies and explicit browser binaries only after checking disk/RAM/network needs. Do not globally install browsers/packages or leave servers/browser trees running. Add other tools only for a concrete required check (for example existing accessibility, security or load tooling). Do not perform destructive/live load or security tests against third-party/production targets.

Submit the matrix; fresh QA uses `review-packet` and `qa-review` with actual findings and provenance. These are team attestations, not user approval. Execute applicable cases against the current build and approved matrix; retain commands/tool versions/log paths, fixtures and observed outcomes. Submit results with exact matrix digest/build fingerprint, one outcome per case, attempts, and defects. Missing/skipped/blocked/not-run/xfail and unapproved retry-passes do not count as passes; labels do not multiply a case. Do not hide failures by deleting cases or unexplained N/A. Matrix changes invalidate reviews/evidence and need independent reassessment.

Quality is strictly MORE THAN 95% of all applicable approved cases, with every critical case passed and no open High/Critical or untriaged severity. 95% exactly fails; zero cases, stale/malformed evidence and unknown severities cannot pass. Closed findings need linked fix/retest proof; false positives need review proof. Evidence provided by the host is an attestation, not cryptographic proof that tests actually ran. Never invent execution. Use QA review for current quality and guide; no routine user approval of every test log.

## Feedback, local guide and completion

After development of each actual managed Stage, deliver a local guide with verified setup/run/stop/cleanup steps and prerequisites, ports, sample data, environment variables without secret values, expected output and known limitations. Bind it to the tested build. Include Windows/macOS instructions only for supported project targets and distinguish executed from unverified checks.

Run 2–3 independent REAL novice sessions after the Stage, collect sources/observations anonymously as appropriate, severity and triage. The owner reviews the batch in the trusted user channel; fake participants and agent simulations never pass this gate. Resolve High+ or unknown findings and rerun affected QA and human checks when the build changes. Medium/Low feedback may enter next Stage backlog within the agreed acceptance rules.

`continue` moves through quality, guide, real feedback and handoff checkpoints. Completion requires current QA, guide, reviewed real feedback, handoff review and no unresolved owned workloads or UNKNOWN actions. Do not label a Stage complete while waiting for people. Give a coherent development-complete report with the exact remaining human checkpoint. The final user handoff presents outcomes, traceability, tests, local guide, cleanup, remaining issues and queued backlog together.

## Runtime isolation and resource lifecycle

Honor inherited version constraints. `doctor` inspects .python-version, runtime.txt and pyproject.toml, reports conflicts and gives step-by-step project-local setup using existing exact runtimes, pyenv on macOS or pyenv-win on Windows. A venv isolates packages, not Python versions. Never replace global Python or silently edit PATH, shell profiles or shared packages. Prefer the repository's lockfile/package manager; record compatibility limitations. Project-builder's bundled interpreter is private to the plugin and is not a client's runtime.

Public `execute` always returns ISOLATION_REQUIRED, including approved recipes. The supervisor is an internal tested library, not a sandbox for Git/network/credential authority. Do not use host tools to work around that refusal or describe full autonomous heavy/test/server/browser execution as implemented. Prepare work and report the concrete capability limitation; owner-operated execution remains outside plugin automation. Future isolated drivers must have measured RAM/disk estimates and timeouts. Unknown footprint is denied; admission reserves machine capacity globally. Internal supervision waits and closes owned workloads; no intentional fire-and-forget server. Windows uses native kill-on-close Job containment; macOS permits only explicitly reviewed cooperative recipes and cannot contain daemonization/setsid, so unknown/detaching recipes are denied. Native macOS behavior must be reported unverified until actually exercised there.

On success, error, pause, cancel or crash, stop only owned resources identified by ledger and process creation identity. `cleanup` is project-scoped. Stale leases never expire into unsafe double admission; reconcile proof before freeing them. Never kill all node/python/browser processes, delete arbitrary temp directories, prune shared containers or remove the user's reusable environment/data. Temporary scratch is disposable; preserve useful code, guides and test evidence. If ownership or containment cannot be proved, report CLEANUP_PENDING rather than guessing.
